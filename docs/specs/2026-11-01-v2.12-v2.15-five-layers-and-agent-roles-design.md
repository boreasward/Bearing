## 1. 目标

对应 roadmap §1 成功标准第 8、10、11、12 条（原文不再抄录）与 §5「五层与角色」。本项目完成后：

| 层（包） | 交付 | 成功标准 |
| --- | --- | --- |
| 全部 | 五层各成一个包，依赖方向由静态测试守住；旧 `workbench/` 不再存在 | roadmap #101 |
| `data/` + `derivation/` | 数据族适配器注册表（六个现有族 + 财报日 + 财季 + SEC 原文 + 行业归类）、主备源与宿主降级、标准指标注册表、两个注册表生成 Agent tool、「登记补查」 | 第 8 条（v2.12） |
| `analysis/` | 链内「公司研究员」段（`agent-4`）、指定标的或问题的第二入口、研究档案 | 第 10 条（v2.13） |
| `execution/` + `analysis/` | `daily` 新节点 `portfolio`：宿主算组合硬结果、Agent 写取舍；模拟账户决策先过检查（`agent-portfolio-2`）；「今日」与推送多一段 | 第 11 条（v2.14） |
| `optimize/` | roadmap 记录化与系统内 roadmap 页、Agent 只读 tool `get_roadmap`、`daily` 新节点 `propose`（周末批）从证据长出提案、界面批准、实施 brief、Markdown 导出 | 第 12 条（v2.15） |
| 共享 | 四个功能开关（默认开、可单独关、翻动留痕、对比页标分界） | 用户 2026-11-01 |

**不改的口径**：规则 v1、`screen-1`、`regime-2`、`plan-2`、`entry-1`、`timeline-2`、`plan-shadow-2`、`execution-1`、`account-1`、`paper-fill-1`、`follow-plans-1`、`discipline-2`、`tracks-2`、`retro-2`、`review-8`、`monthly-5`、`derivation-1`、知识三件。搬家与注册表包装后这些口径的**数值逐一不变**（§16.1 有对照测试）。所有规则与 Agent 照旧未经验证（Phase 0 Gate HOLD）。

## 2. 路线选择

讨论中列出三条，用户选 B。

| 路线 | 做法 | 取舍 | 结果 |
| --- | --- | --- | --- |
| A：一张图加节点，新代码进新包，旧模块原地不动（可选加「数据层搬干净」） | 注册表放 `data/`，研究员与组合检查进 `analysis/`，提案进 `optimize/`，`workbench/` 不动 | 改动面最小、数值不变最易证明；但五层只落三层，新旧两套注册表并存 | 放弃 |
| **B：先把全部模块搬进五层，再加功能** | 148 个模块按 §4 的清单搬家，常量与事务底座下沉消环，再在新结构上做四版 | 分层一步到位，「加一个数据源等于加一个文件」在包结构上成立；代价是 171 个测试文件、247 条概念卡 `sources:` 路径、18 个 CLI 入口与全部文档一起改，纯搬家的 diff 比四版功能还大 | **用户选定** |
| C：两张图按开关选用（`daily-2` / `daily-3`） | 开关关时跑旧图 | 两套代码各测一遍 | 放弃（讨论前即排除） |

B 的风险靠两条纪律收住：①**搬家与功能分开落**——先完成「纯搬家 + 常量下沉」并证明全部口径数值不变、全量测试通过，再做四版功能（plan 分 Task 时据此切）；②**依赖方向由测试守住**（§4.3），搬完当天就有守护，之后的功能代码不能把环加回来。

## 5. 数据层注册表（v2.12）

### 5.1 适配器接口（`data/registry.py`）

```python
@dataclass(frozen=True)
class Source:
    id: str                                   # 'yfinance' / 'stooq' / 'nasdaq' / 'sec' / 'fred' / 'file'
    fetch: Callable[..., list[dict]]          # fetch(target, *, session, start, end, deps) -> rows；失败抛 FetchError
    policy: FetchPolicy                       # 主源默认 fetch-1；备源 FetchPolicy(backoff_s=())
    note: str                                 # 口径说明（复权、时区、延迟），进数据菜单与概念卡

@dataclass(frozen=True)
class Adapter:
    id: str                                   # data_fetch_runs.family 的取值
    title: str; purpose: str
    kind: str                                 # 'fetched' | 'manual'
    per_ticker: bool
    table: str                                # 落库表名（只追加）
    sources: tuple[Source, ...]               # 主源在前；长度 1 或 2
    fallback_kinds: frozenset[str]            # 触发备源的 error_kind，默认 {timeout, network, http_5xx, http_429, empty}
    targets: Callable[[Any, str], list[str]]  # targets(conn, scope) ；scope ∈ {'daily','screen_new_members','manual','research'}
    store: Callable[..., dict]                # store(conn, rows, *, target, source_id, now) -> {'inserted', 'existing', 'latest'}
    latest: Callable[..., dict]               # latest(conn, targets, *, cutoff_at) -> {target: latest_at}
    lagging: Callable[[Any, date], bool]      # 滞后口径（原 families.lagging 的分支）
    coverage_note: str
    tool: ToolSpec | None                     # 不为空 → 生成 request_data 的可选 family
    concept: str                              # 概念卡 id（family.<id>）
    lock: bool = True                         # 是否持 data_family:<id> 锁
```

`run_adapter(adapter, targets, *, scope, trigger, run_id, session, now, deps, tally=None) -> Tally`：逐目标按 `sources` 顺序尝试，第一个源成功即 `store`；主源最终错误的 `kind ∈ fallback_kinds` 且 `backup_sources` 开关开着、且有第二个源时试备源；目标明细写 `source_used`、`fallback = {'tried': bool, 'reason': 主源原因 | None}`、`attempts` 为两个源的尝试合并。`collect` 节点、筛选新成员补采、数据菜单手动拉取、研究请求补采、`request_data` 队列处理都调它。

### 5.5 补查队列的处理（`agent` 节点尾部）

1. 单元全部跑完后，读本 `run_id` 的 `data_requests(status = 'queued')`，按 `(family, ticker)` 去重。

3. 按族持锁、`run_adapter(scope = 'data_request')`，每个请求行更新 `status = fetched | failed`、`rows`、`fetch_run_id`（`data_requests` 允许状态更新，模式同 `paper_orders`：只许 `queued → 终态` 一次）。
4. 有新行的目标所属单元重跑一次（D19）；重跑单元的 `agent_runs.detail.via = 'data_request'`，`data_requests.rerun_run_id` 指向它；每单元每天至多一次重跑。

**输入**（HumanMessage）：单元头（标的、信号日、分层、截止时间）+ `## 研究范围`（只看基本面与披露；不写价位）+ 第二入口时的 `[fact:question]`。

**提示词要点**（`RESEARCH_PROMPT`，实施时逐字写进 `research.py`）：只用工具返回的事实；每条事实注明种类；没取到的数据写进 `blocked`，不得写成「不存在」；不给买卖建议；引用只认本阶段的 `call:N`；输出 JSON。

**输出 schema**（宿主校验 `check_research`，失败整段 `rejected`，不阻断单元 D23）：

```json
{
  "facts": [{"text": "≤200 字", "kind": "disclosure|guidance|price_fact|user|inference", "refs": ["call:N"]}],   // 1–12 条；inference 至多 3 条且必须引 ≥1 条非 inference 的事实
  "risks": [{"text": "≤200 字", "refs": ["call:N"]}],                                                         // 0–6 条
  "blocked": [{"what": "缺什么", "why": "工具返回的原因"}],                                                        // 0–6 条
  "summary": "≤300 字"
}
```

**传给提议者与反方**：`[fact:research]` 段 = `summary` + 编号的 `facts` / `risks` / `blocked`（每条带原 `call:N`）；提议者引用研究员的事实时写该 `call:N`（同一 Recorder，seq 连续，`refs('propose')` 扩成 `refs('research') ∪ refs('propose')`）；反方可引用全部阶段。`plan_check.check_plan` 对 `agent-4` 增加：`thesis` 至少一条引用 `research` 阶段的 ref**或**`output.research.status ≠ 'ok'`（研究员失败时豁免）。

**版本**：`AGENT_V4 = 'agent-4'`；`agent_runs.output` 新增 `research` 键；`agent_tool_calls.phase` 加 `'research'`；`reasoning` 视图多一节「公司研究」。

### 6.2 六个新工具（研究员专用，D24）

| 工具 | 读源 | 截止时间 | 返回 |
| --- | --- | --- | --- |
| `get_fundamentals(ticker)` | `us_research_observations(financials)` → `derivation/indicators/fiscal.financial_series` | `first_seen_at ≤ cutoff_at` | 最近 8 个财季：`revenue / gross_margin / operating_income / eps_diluted / fcf`（有则给）、`period`、`form`、`accession`、同比 |
| `get_guidance(ticker)` | `us_research_observations(guidance)`（手工录入） | `first_seen_at ≤ cutoff_at` | 现行指引条目与对应实际值比较 |
| `get_filings(days)` | 现有 | 现有 | 不变 |
| `get_filing_facts(filing_id)` | `us_research_observations(filings).payload.analysis` | `first_seen_at ≤ cutoff_at` | `facts`、`guidance`、`developments`、`risks`（含原文 `quote` 与 `locator`）、`warnings` |
| `get_filing_text(filing_id, section)` | 本地原文文件（`filings.file_path`） | `downloaded_at ≤ cutoff_at` | `section ∈ {item_1a, item_7, item_2_02, ex_99_1, summary}`；返回 ≤ 6000 字的节选 + `sha256` + 字节范围；没有该节返回 `error` |
| `get_sec_hits(days)` | `news_items(source = 'sec_8k')` + SEC 监控状态里的 `analysis`（已落 `us_research_observations`） | `fetched_at ≤ cutoff_at` | 最近 `days`（≤ 90）天的 8-K 命中与正文事实摘要 |

`get_filing_text` 的节选规则（Item 定位用标题正则，取不到就 `error`，不猜）与 `sha256` 一起记在 `agent_tool_calls.result`，引用校验照旧按 `call:N`。

### 6.3 第二入口（`analysis/research_requests.py`）

- `create(ticker, question, *, request_id, now)`：校验标的（`stock_id`）、问题 ≤ 500 字；写 `research_requests(status = 'queued')`；`daily` 未运行且开关开 → `runner.submit('research', …)`；否则留队列（§10 `agent` 节点处理）。重复 `request_id` 回放。
- `run(request_id, *, now, deps)`：①状态 `running`；②补采：对该标的按注册表跑 `bars / news / sec_filings / earnings / fundamentals / sec_text / sector`（`scope = 'research'`，各写一行 `data_fetch_runs(trigger = 'manual_research')`）；③冻结 `cutoff_at`；④以 `mode = 'research'` 跑 `agent-4` 链（研究员 + 提议者 + 反方 + 校验），`[fact:question]` 带问题，工具白名单同批处理；⑤写 `agent_runs(mode = 'research')`、`research_versions` 一行（`status = concluded`；研究员 `blocked` 非空且提议者 `action = wait` → `waiting_data`）；⑥按 D27 决定是否开链或触发复查；⑦`request_data` 的请求在本入口**同步处理**（预算内），有新行则立刻再跑一版（至多一次）。
- 失败：模型不可用 / 额度 / 超时 → `research_versions` 写 `status = 'error'` 行与原因，请求回到 `queued` 等下一次批处理（至多重试 3 次后 `closed / max_attempts`）。
- 预算：`RESEARCH_DEADLINE_S = 900`；token 计入当日总量；每天手动研究上限 `RESEARCH_DAILY_MAX = 5`（超出 409 `research_quota`）。

### 6.4 研究档案

`research_requests` 一行 = 一份档案；`research_versions` 是它的版本链。页面（§13.2）展示：问题、标的与期限、触发来源（手动 / 批处理）、证据截止时间、状态、预算消耗（token、秒）、结论版本列表（每版：论点、事实与来源按种类分组、催化与时间、反证与替代解释、价格与情景、下一步、下一次复查条件）、关联链（若开链）。批处理链里的研究员段**不**建档案，只在推理视图里看。

## 7. 组合经理（v2.14）

### 7.1 宿主组合检查（`execution/portfolio.py`，纯函数）

```python
check(*, session, plans, positions, pending, cash, equity, params, sectors) -> PortfolioResult
```

- `plans`：当天全部有效 Agent 计划的链头版本（`timeline-2` 状态 `entry` 的链 + 持仓链的最新版），每条带 `ticker`、`chain_signal_date`、`entry_high`、`stop`、`sizing`（按本账户参数 `max_shares` 重算）；`positions` / `pending` 来自本账户账本；`sectors = {ticker: group}`，缺归类的标的 `group = None`。
- 输出 `PortfolioResult`：
  - `exposure_by_sector`: `{group: {held_value, pending_value, candidate_value, share_of_equity}}`，`None` 组单列「未归类」；
  - `verdicts`: 每条计划 `{plan_id, ticker, group, verdict: 'ok' | 'blocked' | 'deferred', reasons: [...], order}`，`reasons ⊆ {sector_cap, max_per_sector, single_cap, total_cap, insufficient_cash, held_ticker, max_positions}`；
  - `conflicts`: 互斥组 `[{group, plan_ids, rule: 'max_per_sector'}]`；
  - `order`: 贪心装入顺序（D30：按 `chain_signal_date` 升序，再按 `ticker`），`deferred_by_cash` 的计划 `order = None`；
  - `params_used`、`version = 'portfolio-check-1'`。
- 判定在宿主；函数不读库、不调模型；与 `paper_strategies.max_shares` 共用同一组上限函数。

### 7.2 节点 `portfolio`（`workflow/nodes/portfolio.py`）

1. 非交易日或开关关 → `skipped`。
2. 冻结 `cutoff_at`；读当天有效 Agent 计划（`execution/chains`）、`sector_classifications` 最新行。
3. 对真实账户与每个 `active` 模拟账户：读账本（`account_books`）、`effective_params`，调 `check`，写 `portfolio_checks` 一行（`account_id, session, run_id, cutoff_at, result JSONB, version`）。
4. 真实账户：若模型可用，调 `analysis/agent/pm.run_pm(result, evidence)`（`mode = 'pm'`，`agent-pm-1`，工具 `get_concept`、`get_knowledge`、`get_indicator`、`get_market_context`）；输出 `{summary ≤ 300 字, ranking: [{plan_id, rank, reason}], tradeoffs: [{text, refs}], hold_actions: [{ticker, suggestion: keep|trim|exit, reason}]}`；宿主校验：`ranking` 只能包含 `verdict = ok` 的计划、不得改任何价位或股数、`refs` 为本次 `call:N` 或 `fact:portfolio_check`；通过后写进同一行的 `commentary` 列（允许一次 UPDATE，模式同 `paper_orders`）与 `agent_runs(mode = 'pm')`。失败只记原因，硬结果仍在。
5. `acc.detail.accounts = [{account_id, blocked, deferred, ok, commentary}]`；运行详情按账户分块。

### 7.3 模拟账户接入

- `accounts` 节点的 Agent 自管决策读同 session 的 `portfolio_checks` 行，证据块加 `[fact:portfolio_check]`（`verdicts`、`exposure_by_sector`、`conflicts`、`order`）；`PORTFOLIO_AGENT_VERSION = 'agent-portfolio-2'`，`PORTFOLIO_PROMPT` 加一段「组合检查是硬结果，`blocked` 的计划不能下单」。
- `validate_orders` 新增：买单计划在本账户的 `verdicts` 里为 `blocked` → 拒绝码取其第一个 `reason`（`sector_cap` / `max_per_sector` 新增进 `REJECT_CODES`）；`deferred` 的允许下单（现金检查照旧会拦）。`portfolio_checks` 缺行（节点失败或开关关）时**不拦**，决策 `detail.portfolio_check = 'missing'`。
- 照计划执行账户不读组合检查（对照不变，D31）；对比页把 `follow-plans-1` 与 `agent-portfolio-2` 的分界都标出（D4）。
- 账户参数新增 `sector_cap`（0.05–1.0，默认 0.35）、`max_per_sector`（1–10，默认 3）；`default_params`、`validate_params`、账户页参数表单、`accounts.ts` 类型、`test_accounts_frontend_sync` 同步；真实账户也可改。

### 7.4 呈现

- 「今日」：`GET /api/workbench/today` 的返回加 `portfolio_check: {session, cutoff_at, account: 真实账户, result, commentary, status}`；页面在运行一览之后加「组合检查」`Section`：一句总结（commentary 或「Agent 不可用，只有硬结果」）、按 `order` 排的计划表（标的、行业组、判定、原因、建议先后）、行业敞口条、互斥组；`DataBlock` 五态照用（节点未跑 = `not_computed`，开关关 = `not_computed` 带原因）。
- 推送：`digest.build` 加 `portfolio` 键；`workbench_digest` 在「🆕 新计划」后发一条「🧩 组合检查」：可一起做 N 条、被拦 M 条（原因）、先后与一句理由。
- 「账户 → 对比」：曲线 `markLine`（D4）与表下「分界」列表。

### 8.2 导入与导出

- `config/roadmap/goals.yaml`、`versions.yaml`、`decisions.yaml`、`evidence.yaml`：实施时从 roadmap.md 人工整理（版本 v1、v2.0–v2.15；决策 #1–#113 及本 spec 新增的；证据按 `v2.x-acceptance.md` 的条目摘要并链接文件）。`python -m investment_assistant.optimize.roadmap import --dir config/roadmap`（幂等：已存在同键同内容跳过，内容不同报错不覆盖）。

### 8.3 节点 `propose`（周六运行，`workflow/nodes/propose.py`）

1. 非周六（北京时间）或开关关 → `skipped`。
2. 宿主证据包（`optimize/evidence.py`，纯 SQL 读取 + 纯函数汇总），每段带行 id：
   - `[fact:data_failures]`：近 7 天 `data_fetch_runs` 按 `family × error_kind` 的失败目标数、备源使用数、`partial / failed` 行数；
   - `[fact:agent_quality]`：近 7 天 `agent_runs` 按 `mode × reason` 的拒绝与错误计数、研究员 `blocked` 原因计数、反方条目被提议者修订版采纳的比例、`data_requests` 的 `deferred` 数；
   - `[fact:retro_patterns]`：近 30 天复盘卡 lessons 与知识草稿按 `scope` 的重复计数（≥ 2 次的）；
   - `[fact:route]`：`roadmap_versions` 中 `user_acceptance_pending` 超过 30 天的条目、主指标最近 3 个月是否触发流程复查；
   - `[fact:open_proposals]`：未决提案列表（避免重复）。
3. Agent（`agent-optimize-1`）输出 `{proposals: [{source, title, change ≤ 500 字, rationale ≤ 500 字, evidence_refs: ['fact:data_failures#<id>', …], expected ≤ 200 字, acceptance ≤ 300 字}]}`，0–3 条；宿主校验每个 `evidence_refs` 指向证据包里存在的行 id，与未决提案标题去重；写 `roadmap_proposals`。
4. 推送：周六的 `push` 节点在本节点之前，所以提案进**下一次**周度复盘推送（`review-8` 的消息末尾加「本周提案 N 条，到 roadmap 页查看」）。

### 8.4 批准与 brief（`optimize/proposals.py`、`optimize/briefs.py`）

- `decide(proposal_id, decision, *, reason, request_id, now)`：`approved` → 同一事务写 `roadmap_versions`（`version_id` 由你在界面填，默认下一个未用的 `v2.x`；`status = planned`；`scope` = 提案的 `change`，`exit_conditions` = `acceptance`）与 `roadmap_decisions`（编号自增，问题 = 提案标题，决定 = 批准 + 理由）；然后 `runner.submit('brief', …)`。`rejected` 只写状态与理由。
- `brief.run(version_id)`：证据 = 提案全文 + `get_roadmap` + 相关概念卡；输出 Markdown：背景与证据、改什么（数据 / prompt / 节点 / 指标，分别指出建议动的模块与 prompt 段）、不改什么、验收、风险；落 `roadmap_briefs`；页面可重试。
- 「批准前无变更」核对（`optimize check`）：`proposed` 的提案在 `roadmap_versions.proposal_id`、`roadmap_briefs.proposal_id` 均无引用；每天 `check` 跑一次，结果进运行报告。

### 8.5 `get_roadmap` 工具

`get_roadmap(section: 'goals' | 'versions' | 'decisions' | 'proposals', query: str | None)`：返回 `created_at ≤ cutoff_at` 的各记录最新版本，`versions` 可按 `version_id` 过滤，`decisions` 可按关键词；返回带 `ref = 'roadmap:<表>:<id>@<version>'`，可作引用。白名单见 D37。

## 15. 出错与降级

| 场景 | 行为 |
| --- | --- |
| 主源失败、备源也失败 | 目标明细记主源原因、`fallback = {tried: true, reason}`；族状态按 `classify` |
| 备源返回但口径可疑（Stooq 日期晚于最近已收盘交易日、OHLC 不满足 `low ≤ open/close ≤ high`） | 该目标按 `parse` 失败处理，不落库 |

## 18. 已知限制

- 备源只有日线与财报日；资讯、SEC、FRED、财季、原文、行业归类单源。
- Stooq 行的 `adj_close` 是沿用比例的近似值；只在主源失败那天出现，主源恢复后被 revision 取代。
- 两套均线口径（`close` / `adj_close`）并存；相对强弱基准一个 SPY 一个 QQQ。
- 研究员只看已入库的披露：池外标的首次研究时财季与原文要先下载，`blocked` 可能很多。
- `get_filing_text` 的节定位靠标题正则，取不到就报错，不做模型抽取。
- 组合检查的行业组是 SIC 两位的粗分类；「未归类」不计入上限。
- 组合检查只出建议，不改写、不作废任何单条计划；真实账户不出成交。
- 提案每周一次、至多 3 条；系统不改自己的代码，brief 是给人的。
- roadmap 导入是一次性人工整理，导入后旧 Markdown 冻结；spec 与 plan 仍在仓库。
- 一次发布 `v2.15.0`，四个版本条目同时进入验收，`v2.12.0`–`v2.14.0` 不存在。
